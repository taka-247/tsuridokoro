# 釣りドコロ 開発ロードマップ（MVP）

> 対象: MVP（アイデア検証）フェーズ
> 方針: **最もリスクの高い「AI集計の品質」を最初に潰す**。UIは検証に足る最小限で先に進む。
> 前提スタック: React + TypeScript + TailwindCSS + Headless UI / 最小BFF / Gemini API(Google検索グラウンディング)
> 関連: [SPECIFICATION.md](./SPECIFICATION.md)
> 進捗（2026-11 時点）: Phase 0〜3・5 はほぼ完了。残りは Phase 4 のミニゲーム、Phase 1 のコスト/レート制御、Phase 6。状態は [SPEC §15](./SPECIFICATION.md) も参照。

---

## 全体像

```
Phase 0  設計確定 ── Phase 1  集計API(コア/最大リスク) ── Phase 2  トップページ&フォーム
                                                              │
Phase 5  集計結果ページ ── Phase 4  ローディング/ミニゲーム ── Phase 3  集計結果UI
                                                              │
                                                       Phase 6  仕上げ・検証
```

MVP検証に必須なクリティカルパスは **Phase 1 → 2 → 3**。ミニゲーム(4)・履歴(5)はその後。

---

## Phase 0 — 設計確定（半日〜1日）
**ゴール: 実装前に契約と方針を固める**
- [x] データモデル（[SPEC §9](./SPECIFICATION.md)）を確定（リクエスト/レスポンスJSON）
- [x] 使用モデルを決定（`gemini-3.6-flash`）
- [ ] Web検索回数上限・コスト方針を決定
- [x] BFFホスティング先を決定（Render Web Service）
- [x] Google Maps 埋め込み方式とキー要否を確認（keyless iframe、キー不要）
- [ ] 法務（引用/規約）の懸念点を洗い出し

**完了条件**: JSONスキーマとAPIエンドポイント仕様が文書化されている

---

## Phase 1 — 集計API（コア・最大リスク）（2〜4日）
**ゴール: 入力を渡すと、実在する釣果に基づく構造化JSONが返る**
- [x] BFFに `POST /api/aggregate` を実装（APIキー秘匿）
- [x] Gemini API + Google検索グラウンディング呼び出し
- [x] §9.2 形式で出力させる（プロンプトでJSON指示＋抽出。グラウンディングと `responseSchema` は併用不可のため）
- [x] プロンプト設計（`backend/src/routes/aggregate/prompt.md`。対象リソース指定・広域名除外・ハルシネーション抑制・URL/引用の実在性）
- [x] レスポンス検証（Zod `aggregateResultSchema`、`meta` 入力値はサーバーが上書き）
- [ ] コスト/レート制御（検索回数上限・タイムアウト）

**検証（このPhaseが山場）**: 自分の知っている釣り場で数パターン集計し、
- 出典URLが実在するか
- 場所・サイズ・件数がもっともらしいか
- 情報が少ない条件で正直に `low` を返すか
を手動確認。ここで「使えない」なら早期にピボット判断できる。

**完了条件**: curl等でエンドポイントを叩き、妥当なJSONが安定して返る

## Phase 2 — トップページ & フォーム（1〜2日）
**ゴール: フォーム入力 → API呼び出し → SessionStorage保存**
- [x] 魚種 / 県市町村 / 過去何日分 のフォーム（Headless UI）
- [x] バリデーション（未入力。市町村まで必須のため広域指定は発生しない）
- [x] 集計ボタン → `/api/aggregate` 呼び出し
- [x] 結果を localStorage(`tsuridokoro:results`) に保存（その週の日曜日終わりで失効）
- [x] エラー時のハンドリング（エラートースト）
- [ ] タイムアウト・専用の再試行ボタン

**完了条件**: 集計を実行するとJSONが取得・保存される（UIは素でよい）

---

## Phase 3 — 集計結果UI（2〜3日）
**ゴール: 集計結果を分かりやすく表示（MVPの見せ場）**
- [x] オススメ上位5ヶ所カード（期待度メーター・名前・サイズ・出典・特記事項）
- [x] 日別釣果数の棒グラフ（軽量に。0件日も描画）
- [x] Google Map 埋め込み（緯度経度 or 地名クエリ）
- [x] 上位5件以外の一覧（仕様変更により釣り場名のみ・トグルなし）
- [x] `dataConfidence: low` 時の注意表示・空状態のデザイン

**完了条件**: 実際の集計結果が仕様どおり表示され、他人に見せて感想を得られる

---

## Phase 4 — ローディング & ミニゲーム（1〜2日）
**ゴール: 集計待ちを退屈させない**
- [x] 集計中ローディング表示（`LoadingOverlay`）

- [x] 集計完了で自動的に結果（`/results`）へ遷移

**完了条件**: 集計中に遊べて、完了時に結果が出る

## Phase 5 — 履歴ページ（1日）
**ゴール: 過去の集計を見返せる**
- [x] ドロップダウン（ラベル: `魚種・市町村・過去N日` ＋ 集計時刻）で選択（`/history`）
- [x] 選択で結果UIを再表示（Phase 3 のコンポーネント再利用）
- [x] 履歴が空のときの表示

**完了条件**: 同じ週の間、過去の集計を切り替え閲覧できる

---

## Phase 6 — 仕上げ & 検証（1〜2日）
**ゴール: 検証に出せる品質にする**
- [ ] レスポンシブ（スマホ第一）の調整

## 目安工数
おおよそ **2〜3週間**（1人・専業換算）。最大の不確実性は Phase 1。ここを最初に検証することで、以降の投資判断（続行/ピボット/中止）を早期に下せる。

## MVP後（優先度順の候補）
1. 利用反応が良ければ → v2オプション（天候・月齢・風向き）
2. コストが問題化 → 事前ingestion + キャッシュ（[SPEC](./SPECIFICATION.md) 4.4 参照）へ移行
3. リピート利用が見えれば → アカウント/サーバー永続化・共有機能
